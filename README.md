# Savivah backend (Python / FastAPI)

A ground-up rebuild of the previous Node/Express backend, following the
layered FastAPI + PostgreSQL + Redis architecture: FastAPI is the API
boundary, business rules live in `app/services/`, PostgreSQL is the only
source of truth, Redis accelerates reads and holds rate-limit state, and
scheduled work runs in `app/workers/`.

Every module in this repo was actually imported and boot-tested against a
running FastAPI instance while building it — including catching two real
missing dependencies (`email-validator`, `requests`) that only surfaced
once the full app was imported, not just syntax-checked.

## Setup

```bash
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env            # fill in real values
psql -d savivah -f schema.sql
python scripts/create_admin.py  # create your first admin account
python scripts/register_ipn.py  # once — copy the printed ipn_id into .env
uvicorn app.main:app --reload --port 8000
```

Interactive API docs (auto-generated by FastAPI from the Pydantic schemas)
are available at `http://localhost:8000/docs` once running.

## What changed from the previous Node backend

- **Admin is now a fully separate concern.** There's no more
  `@savivah.co.ke` domain trick — that was flagged as a real security gap
  (anyone could type that domain with no email-ownership check). Admin
  accounts live in their own `admin_users` table, are created only via
  `scripts/create_admin.py`, log in through `/api/admin/auth/login` (a
  completely different endpoint from customer/seller login), and are signed
  with `ADMIN_JWT_SECRET` — a different key from `JWT_SECRET`. A leaked
  customer-token secret can never be used to forge an admin session.
- **Admin tokens are short-lived (10 min) with a refresh flow**
  (`/api/admin/auth/refresh`), matching the "short-lived access + secure
  refresh" control from the architecture spec. Customer/seller tokens are
  15 minutes.
- **2FA hook is in place** (`admin_users.totp_secret` + `pyotp`) — enable it
  per-admin by setting that column; login will then require a `totpCode`.
- **Product listing is cursor-paginated and Redis-cached.** The frontend
  must request bounded pages (`?limit=24&cursor=...`), never the whole
  catalogue. Redis is read-through only — PostgreSQL is queried on every
  cache miss and remains authoritative; cache entries are actively
  invalidated on product create/update, with a short TTL as a safety net
  regardless.
- **Checkout is a single PostgreSQL transaction** that locks each product
  row (`SELECT ... FOR UPDATE`) before decrementing stock, so two
  simultaneous checkouts can never both oversell the same last unit — this
  wasn't explicitly guarded against in the Node version.
- **Login/register/admin-login are rate-limited** via Redis (sliding window
  by IP), per the traffic-protection section of the spec.
- **Payment IPN/callback handling is explicitly idempotent** — processing
  the same Pesapal notification twice is safe by construction (status
  writes are just overwrites; escrow confirmation only fires the
  `pending_payment -> escrow_held` transition once, guarded by the current
  status).
- **The scheduled payout sweep is a real background worker**
  (`app/workers/payout_sweep.py`) wired through APScheduler in `main.py`'s
  lifespan handler, rather than an inline `setInterval`-equivalent — this is
  the natural seam to swap in Celery + Celery Beat later without touching
  `app/services/escrow.py` at all.
- **Every payout dispatch and dispute resolution now records which admin
  did it** (`payouts.dispatched_by`, `disputes.resolved_by`) — a basic
  audit trail for sensitive financial actions, per the spec.

## Known gaps carried over from the previous version (not yet fixed here either)

- **Fargo's webhook payload shape is still an assumption** — `FargoWebhookPayload` in `app/schemas/order.py` is the same guessed shape as before. Confirm against Fargo's real docs before relying on it.
- **No real M-Pesa B2C payout call** — `release_payout()` in `app/services/escrow.py` only creates a `payouts` row; a human still sends the actual money and clicks "Mark sent."
- **No Pesapal refund API call** — a FAILED/REVERSED payment status currently isn't acted on at all (see the connection reference doc for detail).
- **Fargo webhook signature verification is a TODO** — the header is checked for *presence* if `FARGO_WEBHOOK_SECRET` is set, but the actual signature is not yet verified, since Fargo's signing scheme isn't confirmed.

## Deployment note

This is structured the same way as the previous Node backend for Render:
a `render.yaml` blueprint would define this as a Python web service
(`uvicorn app.main:app --host 0.0.0.0 --port $PORT`) plus a PostgreSQL
database plus a Redis instance (Render offers managed Redis/Key Value
under "New +"). Ask if you'd like that blueprint file generated next.
